# ESP32-S3 猫咪摄像头开发

## 核心原则

把串口、摄像头、Wi-Fi、TF、事件、AI、音频依次做成可独立验证的检查点。一次只增加一个子系统；失败时退回最近通过的检查点。

设备负责稳定取图、预览、事件缓存与上传，后端负责猫检测和行为分析。不要让 ESP32-S3 承担 24 小时 1080P H.265 连续录像；需要全天录像时改用专用 IPC SoC、硬件编码器或外部录像设备。

## 项目目标与非目标

目标：

- 设备可 24 小时在线，并在局域网通过 Wi-Fi 实时查看猫咪。
- 把事件照片和短片可靠保存到 TF；断网时继续记录，恢复后补传。
- 把代表帧交给后端完成猫检测与行为分析，不让云端故障阻塞本地记录。
- 视频链路稳定后加入 INMP441、MAX98357A 和 4Ω 3W 喇叭，实现半双工对讲。
- 用阶段化证据把开发板原型推进到可验证、可产测的量产 PCB。

非目标：

- ESP32-S3 上的 24 小时 1080P H.265 连续录像。
- 第一版同时启用所有功能，或在未核对原理图时承诺最终音频 GPIO。
- 用未经测量的 FPS、AI 准确率或续航数字作为产品承诺。

## 硬件边界与引脚占用

### 当前参考板的已知映射

下表来自当前项目参考原理图/Pinout。烧录前必须与到手 SKU、商家 OV5640 例程及实际原理图逐项核对；成功上传固件不等于映射正确。

TF / microSD 当前约束：`GPIO40 = DAT0/DATA`、`GPIO39 = CLK`、`GPIO38 = CMD`，优先按 SDMMC 1-bit 模式验证。

### 音频预留规则

INMP441 需要 BCLK、WS/LRCLK、麦克风数据输入；MAX98357A 需要 BCLK、LRC/WS、功放数据输出，最好另有 SD/EN。可评估共享 BCLK 与 WS，但数据输入和输出必须分开，录音时关闭功放以降低啸叫与电源噪声。

在完整原理图和板级冲突表确认前，保持音频 GPIO 为“未分配”。GPIO4～18 中上述摄像头引脚和 GPIO38～40 不得作为音频候选；还要排除 Flash/PSRAM、启动绑带、USB/JTAG、板载 LED 与其他外设占用。不要用“假设另一块板上空闲”为当前项目提供示例接线表，因为示例很容易被误当成已验证方案。选定后分别做启动、相机、TF、Wi-Fi 与音频组合测试。

## 目标架构

```text
OV5640 JPEG -> 有界帧队列 -> 局域网预览（可丢帧）
                         -> 事件环形缓存 -> TF 写入任务（高优先级）
                         -> 候选图上传 -> 后端猫检测/行为分析

INMP441 -> 监听状态 --互斥状态机-- 讲话状态 -> MAX98357A -> 4Ω 3W 喇叭
```

所有队列必须有长度上限，所有 I/O 必须有超时。TF 慢、客户端断开或后端离线时，可以降低/丢弃预览，但不能拖死取帧或事件落盘。主要大缓冲尽量在启动阶段分配，并持续记录内部 RAM、最大连续块与 PSRAM 余量。

事件短片优先用 JPEG 序列或 MJPEG/AVI，并附 JSON 元数据；需要 H.264/H.265 时交给后端转码。不要把 5MP 传感器等同于 5MP 实时视频能力。

## 分阶段开发与验收门

严格按阶段推进；未通过当前验收门，不叠加下一子系统。

### 阶段 0：板卡与工具链确认

1. 记录板卡、OV5640、Flash、PSRAM、原理图与商品 SKU。
2. 在 macOS 检查 USB 设备和 `/dev/cu.*`；先换数据线/端口，再判断是否需要驱动。
3. 让用户选择工具链：Arduino 用于最短首烧路径；ESP-IDF 用于生产化组件控制、调试、OTA 与长期维护。不要静默替用户决定。
4. 建立 `hardware-profile` 配置，集中存放经验证的引脚与板型，不把映射散落在业务代码。

验收：确认串口设备、板型、工具链版本与硬件事实表；所有未知项显式标注。

### 阶段 1：串口与基础稳定性

只烧录 115200 串口程序，验证上传、复位、启动日志和复位原因。记录端口、上传速度、BOOT/RESET 操作和电源条件。

验收：连续冷启动 20 次；无乱码、无启动循环；每次都有版本、复位原因、Flash/PSRAM 检测日志。

### 阶段 2：OV5640 单独取图

关闭 Wi-Fi 和 TF，从 QVGA/VGA JPEG、单帧缓冲开始。确认传感器 ID，再逐步增加分辨率和帧缓冲；每次仅改一个变量。归还每条成功/错误路径上的 frame buffer。

验收：VGA/SVGA 连续取图至少 2 小时，无花屏、初始化失败、不可恢复超时或内存单向下降；保存一组可追溯测试图与串口日志。

### 阶段 3：Wi-Fi 实时查看

先实现同一局域网的 HTTP MJPEG 或逐帧 JPEG 预览，再增加单张高分辨率抓拍。实现 Wi-Fi 自动重连、客户端断开清理、超时、看门狗、SNTP 校时和未校时时的唯一文件序号。

按 VGA、720P、1080P 分别记录 FPS、端到端延迟、RSSI、掉帧、内部 RAM/PSRAM 和温度。默认工程目标：VGA 达到约 10 FPS 且同网 p95 延迟低于 1 秒；720P 是否作为预览档由实测和用户观感决定；1080P/5MP 优先定位为抓拍，不把它设为持续流硬门槛。

验收：客户端反复连接/断开 100 次无资源泄漏；路由器重启后自动恢复；预览断开不影响摄像任务。

### 阶段 4：TF 事件存储

先做独立挂载和连续写测试，再与相机组合。事件采用有界环形帧缓存，默认保存事件前 3～5 秒和后 10～20 秒；根据 PSRAM 实测调整。文件先写 `.tmp`，完成同步与关闭后再改为正式名；启动时处理残留临时文件。

每个事件至少包含设备 ID、事件 ID、起止时间、触发原因、帧参数、校验/完整性状态。达到容量阈值后删除最旧的已完成事件；卡满、慢卡、坏卡、拔卡均不得阻塞摄像与网络。

验收：连续写入/轮转 24 小时无文件系统错误；随机断电测试至少 100 次，重启后可挂载或进入明确的降级状态；正式事件可读取且元数据可追溯。

### 阶段 5：24 小时在线与恢复

加入有界队列、任务心跳、分层恢复状态机、看门狗、复位原因、崩溃摘要、内存水位、TF 最长写延迟、网络中断时长和摄像头重启次数。恢复顺序优先局部重启子系统，最后才整机重启。

验收：原型连续运行 72 小时无人干预；相机、TF、网络分别故障注入后自动恢复或明确降级；无内存泄漏趋势、无死锁。定型前完成 7 天老化、弱网、满卡、坏卡、断网 12 小时补传和反复断电测试。

### 阶段 6：后端 AI 猫检测与行为分析

设备只产生候选事件：帧差、区域变化或低频抽帧均可。先上传缩略图/代表帧；后端返回猫/非猫、置信度、目标框、行为标签与事件 ID。使用相同事件 ID 做幂等去重；后端不可用时先落 TF，恢复后按优先级补传，不阻塞本地事件。

验收：使用真实安装位置的白天、夜间、逆光、空场、人经过数据；分别统计漏检率和误报率；连续活动可合并事件；阈值可配置并回滚。项目未给数据集前，不虚构准确率承诺。

### 阶段 7：半双工对讲

只在视频、TF、网络和 OTA 稳定后加入 INMP441、MAX98357A 与 4Ω 3W 喇叭。状态机至少包含 `LISTEN`、`MUTING`、`TALK`、`RECOVER`；切换时先静音/关闭功放，再重配 I2S。网络中断或超时必须退出 TALK 并关闭功放。

验收：监听/讲话切换 500 次无 I2S 卡死或持续爆音；对讲期间视频与事件落盘仍可工作；记录端到端延迟，原型目标小于约 500 ms；功放峰值负载不触发棕断。

## 故障排查顺序

先保存完整首个错误、复位原因和最小复现，再降到单子系统；不要用随意增加延时掩盖根因。

| 症状 | 首轮检查 | 隔离动作 |
| --- | --- | --- |
| 没有串口 | 数据线、USB 设备、端口、板型 | 仅连板卡，换线/端口；确认 USB 芯片后再装驱动 |
| 上传卡在连接 | 端口、板型、上传速率、BOOT/RESET | 降低速率，手动进入下载模式 |
| `esp_camera_init()` 失败 | 精确板型、OV5640 ID、引脚、RESET/PWDN、XCLK、PSRAM、电源 | 关闭 Wi-Fi/TF，回到 QVGA 单帧 |
| 黑屏/花屏/噪点 | 数据位映射、PCLK/VSYNC/HREF、XCLK、排线、电源 | 降分辨率/时钟；检查传感器 ID 与信号波形 |
| 开启 Wi-Fi 后重启 | 复位原因、3.3V 压降、PSRAM、DMA/heap | 单独压力测试电源；降低分辨率/帧缓冲 |
| TF 无法挂载 | DAT0/CMD/CLK 映射、1-bit 模式、上拉、格式 | 降 SD 时钟；只跑 TF；换已验证 FAT32 卡 |
| TF 写入拖死视频 | 队列是否有界、写入超时、卡延迟 | 独立 TF 任务；丢预览帧而非阻塞取帧 |
| 长时间后死机 | heap 趋势、最大连续块、frame buffer 归还、队列增长 | 相机/TF/Wi-Fi 分别 24h，再两两组合 |
| 事件丢失/损坏 | `.tmp` 流程、同步关闭、文件索引、断电时点 | 故障注入并扫描残留临时文件 |
| 音频啸叫/棕断 | 功放 EN、共享时钟、地线、供电峰值、布局 | 关闭功放只录音；关闭麦克风只播放 |
| AI 上传影响本地功能 | 上传超时、重试、队列优先级、幂等键 | 断网运行；确认事件仍先落 TF |

## 从原型到量产 PCB

按以下门槛推进，不因“功能能跑”跳过验证：

1. **原型板冻结**：锁定实测通过的分辨率、FPS、TF 模式、功耗、热数据与音频引脚。
2. **原理图 EVT**：核对 ESP32-S3 启动绑带、Flash/PSRAM、USB、OV5640 电源/时钟、TF 上拉与串阻预留、功放独立使能、电源峰值、测试点和调试接口。
3. **PCB EVT**：天线净空；摄像头/TF/I2S 时钟远离天线和敏感模拟线；摄像头、TF、功放附近就地去耦；保留电流测量和关键波形测试点。
4. **EVT 验证**：做相机、PSRAM、Wi-Fi、TF、麦克风、扬声器、电源、温升、ESD/异常断电的单项与组合测试。
5. **DVT 定型**：固定 BOM、替代料、OV5640 与 TF 兼容清单、外壳热/声学/天线表现；完成 7 天老化和故障注入。
6. **PVT/量产**：准备产测固件和治具，逐台记录相机 ID、坏点/图像、PSRAM、Wi-Fi RSSI、TF、音频、电流、温度；烧录双 OTA、唯一设备身份和可追溯序列号。

量产固件应包含双 OTA、签名/回滚、配置版本迁移、恢复出厂、唯一设备凭据、崩溃与复位信息持久化。不要让所有设备共享长期密钥。

## 常见错误

- 从“ESP32-S3-CAM”通用名称猜摄像头引脚。
- 把参考图中的 OV2640 配置直接用于 OV5640。
- 在未核对冲突时给 INMP441/MAX98357A 分配 GPIO，尤其误用 GPIO4～18。
- 拒绝当前冲突后，又给出其他假设板型的示例 GPIO，导致示例被误接。
- 同时启用摄像头、Wi-Fi、TF、AI 上传和音频后才开始排错。
- 用连续 1080P/H.265 录像衡量该原型是否成功。
- 只测几分钟，不记录内存、温度、复位原因和 TF 写入尾延迟。
- 云端离线时让上传阻塞本地事件落盘。
- 把能编译、能上传或偶尔能出图当作阶段验收通过。
